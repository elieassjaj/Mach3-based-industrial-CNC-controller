# CNC5AX-ETH Motion Engine

## 1. Purpose

This document defines the **non-negotiable requirements, constraints, interfaces, and design objectives** for the motion-control subsystem of the CNC5AX-ETH controller.

The purpose of this document is **not** to prescribe a specific implementation.

The final motion-engine architecture, algorithms, timer allocation, DMA strategy, buffering mechanism, interpolation method, and real-time scheduling strategy must be selected during firmware development based on:

- Mach3 SDK behavior
- Project requirements
- STM32F407 capabilities
- STM32 official documentation
- Real-time performance analysis
- Determinism
- Measured timing margin
- Reliability and safety

The implementation must satisfy all fixed requirements in this document with a substantial engineering margin.

# 3. Motion Axes

The controller provides five real motion axes:

```text
X
Y
Z
A
B
```

All five axes are part of the required motion-control subsystem.

The requirement to guarantee three axes at maximum speed does **not** mean that the remaining two axes are optional or lower-priority.

The final implementation must support all five axes.

# 4. STEP Outputs

## 4.1 Electrical Behavior

All STEP outputs are:

```text
Active High
```

A STEP event is generated by a transition from:

```text
LOW → HIGH
```

The external stepper/servo drivers are primarily sensitive to the **rising edge** of the STEP signal rather than the exact pulse width.

The STEP output therefore must guarantee a clean and deterministic rising edge.

---

## 4.2 Maximum STEP Rate

The maximum reliable target STEP frequency is:

```text
2 MHz
```

This means a maximum nominal STEP period of:

```text
500 ns
```

The 2 MHz figure is the project-level maximum target for reliable operation and must be treated as a hard performance requirement.

### Multi-Axis Requirement

The motion engine must be designed so that:

```text
At least 3 axes
```

can operate simultaneously at:

```text
2 MHz STEP rate per axis
```

while maintaining reliable and deterministic operation.

This is a **minimum guaranteed capability**.

The remaining two axes must remain fully functional and must not be architecturally disadvantaged simply because the minimum simultaneous 2 MHz requirement is specified for three axes.

A stronger implementation that supports all five axes simultaneously at or near 2 MHz is preferable, but it must not be assumed or claimed without verification.

---

# 5. STEP Pulse Width

The external stepper/servo drivers are primarily sensitive to the rising edge of the STEP signal.

Therefore, the exact STEP pulse width is not a primary system-level constraint.

The design should nevertheless maintain a pulse width comfortably above:

```text
100 ns
```

as a practical safety margin.

The implementation must ensure that the generated pulse is:

- Clean
- Monotonic
- Deterministic
- Free from unintended glitches
- Long enough to satisfy the external driver's requirements

The exact pulse-generation method must be selected by the firmware implementation.

---

# 6. DIR Outputs

All DIR outputs are:

```text
Active High
```

The authoritative DIR pin mapping is defined in:

```text
Docs/PINOUT.md
```

The motion engine must treat the direction signal as a hardware-timed part of the motion-generation system rather than as an unrelated background GPIO operation.

---

# 7. DIR Timing Requirements

The minimum required timing margin for each direction change is:

```text
DIR setup time:  200 ns minimum
DIR hold time:   200 ns minimum
```

The implementation must guarantee at least these values between a DIR transition and the relevant STEP edge.

The actual firmware implementation should preferably provide additional margin rather than operating exactly at the minimum.

Conceptually:

```text
DIR change
    │
    ├────── ≥ 200 ns ──────►
    │
    │                        STEP rising edge
    ▼                              ↑
 DIR stable                first STEP event
```

The exact timing mechanism must be determined during implementation.

Software delays should not be used for hard real-time DIR timing when a deterministic hardware-based mechanism is available.

---

# 8. Hardware Timing Requirement

The STEP/DIR subsystem is a **hard real-time subsystem**.

The final architecture must ensure that Ethernet processing, application-level networking, diagnostics, logging, and other non-real-time operations cannot introduce unacceptable timing variation into STEP generation.

The repository architecture already establishes motion timing as a higher-priority concern than non-real-time processing.

The final implementation must preserve this principle.

---

# 9. STEP Pin Hardware Configuration

According to the project hardware definition (`Docs/PINOUT.md`):

```text
STEP_X = PC9
STEP_Y = PA8
STEP_Z = PA9
STEP_A = PA10
STEP_B = PA11
```

These pins have valid timer alternate-function mappings (PA8–PA11 = TIM1_CH1–CH4; PC9 = TIM3_CH4/TIM8_CH4), but per Section 10, they are deliberately configured as plain GPIO outputs and driven via DMA→BSRR rather than via their Alternate Function — because PA8–PA11 share a single TIM1 ARR (period), which would force axes Y, Z, A, and B onto one common STEP frequency.

The exact DMA stream/mask allocation must be taken from the authoritative project pinout and verified against the STM32F407 Datasheet and Reference Manual.

Do not infer timer/DMA assignments from the GPIO names alone.

---

# 10. Preferred Hardware Generation Strategy

The initial design direction is:

```text
Hardware Timer + DMA
```

However, the project does **not** predefine whether the final implementation must use:

- PWM mode
- Output Compare
- Toggle mode
- One-pulse generation
- DMA-driven GPIO/BSRR updates
- Timer + DMA waveform generation
- A combination of the above
- Another hardware-assisted architecture

The final method must be selected by the implementing AI/engineer based on measured and documented requirements.

### Selection Criteria

The chosen implementation must prioritize:

1. Deterministic STEP timing
2. Deterministic DIR timing
3. Low CPU overhead
4. Low interrupt frequency in the hard real-time path
5. Sufficient DMA bandwidth
6. Sufficient timer resolution
7. Multi-axis synchronization
8. Minimal timing jitter
9. Safe handling of direction changes
10. Reliable operation under maximum Ethernet traffic
11. Sufficient margin above the minimum requirements
12. Maintainability and debuggability

Do not select PWM merely because the pins are connected to timer PWM-capable outputs.

PWM is one possible implementation technique, not a mandatory architectural requirement.

# 15. Five-Axis Synchronization

All five axes must be treated as part of one coordinated motion system.

When multiple axes participate in the same motion segment, the generated STEP streams must preserve the required relationship between the axes.

The exact interpolation method must be selected during implementation.

The final implementation should be evaluated for:

- Position accuracy
- Timing accuracy
- Axis synchronization
- Velocity consistency
- Acceleration behavior
- Segment-to-segment continuity
- Maximum step rate
- Jitter
- Buffer behavior

The implementation must not sacrifice multi-axis correctness merely to achieve the maximum STEP rate.

# 17. Ethernet and Motion Separation

The Ethernet subsystem uses:

```text
LAN8720A
    ↓
RMII
    ↓
STM32F407 Ethernet MAC
    ↓
DMA
    ↓
LwIP
    ↓
UDP
```

The project Ethernet documentation defines the network path and explicitly requires that Ethernet processing must not compromise deterministic motion timing.

The motion engine must therefore be isolated from network processing as much as practical.

The preferred conceptual relationship is:

```text
Ethernet
   │
   ▼
UDP / Protocol
   │
   ▼
Motion Command Buffer
   │
   ▼
Motion Engine
   │
   ▼
Hardware Timer / DMA
   │
   ▼
STEP / DIR
```

The Ethernet callback must not become the STEP-generation mechanism.

---

# 18. Real-Time Priority

The final implementation must assign priorities according to actual timing requirements.

The following general priority principle applies:

```text
Hard real-time motion timing
        ↓
Motion state / critical safety handling
        ↓
Motion data preparation
        ↓
Ethernet processing
        ↓
Diagnostics / non-real-time tasks
```

The exact interrupt priority values must be derived from the final implementation and verified experimentally.

Do not choose priorities arbitrarily.

---

# 19. CPU Load

The motion engine must be designed to leave sufficient CPU resources for:

- Ethernet processing
- LwIP
- Mach3 protocol handling
- I/O handling
- Safety monitoring
- Diagnostics
- Status feedback
- Future firmware expansion

The design must therefore avoid unnecessary high-frequency CPU interrupts.

A solution that technically generates 2 MHz STEP pulses but consumes excessive CPU time is not considered a robust solution.

# 21. Motion Safety

# 24. Direction Handling

Direction changes are part of the hard real-time motion path.

The implementation must guarantee:

```text
DIR setup ≥ 200 ns
DIR hold  ≥ 200 ns
```

around the relevant STEP edge.

The final implementation must ensure that:

- DIR cannot change accidentally during a STEP event
- A direction transition does not create a spurious STEP
- The first STEP after a direction change satisfies the required setup time
- The last STEP before a direction change satisfies the required hold time

The exact implementation method is TBD.

# 25. Negative and Positive Motion

Because DIR is Active High, the final implementation must define a consistent relationship between:

```text

Axis sign
        ↓

```

The exact sign convention must be taken from the final machine configuration and Mach3 integration.

Do not assume:

```text
DIR = 1 → positive
DIR = 0 → negative
```

# 26. CoreXY / Kinematic Transformations

# 28. Engineering Objective

The goal is not merely to produce a motion engine that can theoretically reach:

```text
2 MHz
```

The objective is to produce a motion engine that can do so:

- Reliably
- Deterministically
- With low jitter
- With substantial timing margin
- Under maximum expected Ethernet traffic
- With simultaneous multi-axis operation
- Without unsafe race conditions
- Without excessive CPU usage
- Without depending on fragile timing assumptions

The implementation should target **headroom**, not merely the minimum passing condition.

# 29. Required Verification

Before considering the motion engine complete, the implementation must be verified experimentally.

At minimum, testing should cover:

### STEP Timing

- Maximum STEP frequency
- Minimum practical frequency
- STEP pulse width
- STEP edge integrity
- Timing jitter

### Multi-Axis Operation

At minimum:

```text
3 axes × 2 MHz STEP
```

must be demonstrated reliably.

The remaining two axes must also be tested under concurrent operation.

Where practical, test:

```text
5 axes simultaneously
```

under representative worst-case conditions.

### DIR Timing

Verify:

```text
DIR setup ≥ 200 ns
DIR hold  ≥ 200 ns
```

under worst-case operating conditions.

### Ethernet Load

Motion timing must be measured while Ethernet is under realistic and worst-case expected traffic.

### CPU Load

Measure CPU utilization during:

- Idle
- Normal motion
- High-rate motion
- Multi-axis motion
- High Ethernet traffic
- Maximum STEP operation

### Stress Conditions

The final design should be tested with combinations of:

```text
Maximum STEP rate
+
Multiple active axes
+
Continuous Ethernet traffic
+
Motion buffer activity
+
I/O activity
+
Status transmission
```

The objective is to verify that the real-time motion subsystem remains deterministic.

This document is specifically intended to guide AI-assisted firmware development.

The AI must follow these rules.

### Rule 1 — Do not change fixed requirements

The values explicitly marked as project requirements must not be changed by the implementation.

This includes:

```text

STEP Active High
DIR Active High
```

### Rule 2 — Do not invent unspecified requirements

If a required value is not defined here, the AI must not silently create one.

Examples:

```text

Interrupt priority

```

These must either:

1. Be derived from an authoritative source,
2. Be experimentally determined,

### Rule 3 — Read the Mach3 SDK before implementing the host interface

The AI must inspect the complete Mach3 SDK material relevant to motion control before defining:

- Motion command structures
- Host-controller synchronization
- Position handling
- Motion timing
- Feed/velocity handling
- Jogging
- Stop behavior
- Input handling
- Feedback

Do not infer these from generic Mach3 knowledge.

### Rule 4 — Verify every hardware-dependent decision

Before selecting a timer, DMA stream, channel, GPIO mode, or alternate function, verify it against:

```text
PINOUT.md
+
STM32F407 Datasheet
+
RM0090
+
STM32 Errata
```

---

### Rule 5 — Optimize for margin

The implementation should not be optimized merely to reach the specification boundary.

Where feasible, target:

```text
Required performance
        ↓
Engineering margin
        ↓
Measured worst-case performance
```

The final implementation must retain sufficient margin for:

- Interrupt latency
- DMA contention
- Ethernet traffic
- Memory access
- Future firmware additions
- Worst-case execution paths

---

### Rule 6 — Do not force PWM without analysis

The hardware provides timer alternate-function outputs for the STEP pins.

This does **not** automatically mean PWM is the optimal STEP-generation technique.

The AI must compare appropriate approaches and select the one that provides the best combination of:

- Determinism
- Synchronization
- DMA efficiency
- CPU efficiency
- DIR timing
- Multi-axis scalability
- Reliability

---

### Rule 7 — Prefer hardware timing

When a timing requirement belongs to the STEP/DIR waveform itself, prefer deterministic hardware peripherals over software delays or high-frequency polling.

CPU-based timing must not be selected simply because it is easier to implement.

---

### Rule 8 — Measure before claiming compliance

A theoretical calculation is not sufficient to claim:

```text
3 × 2 MHz
```

or any other final performance target.

The final implementation must be tested on the actual hardware.

# 34. Final Design Principle

The motion engine must be treated as the **highest-priority real-time subsystem** of the CNC controller.

The final implementation should follow this principle:

```text
                    MACH3
                      │
                      ▼
                Ethernet / UDP
                      │
                      ▼
               Motion Protocol
                      │
                      ▼
              Motion Processing
                      │
             ┌────────┴────────┐
             ▼                 ▼
        Axis Planning       Buffering
             │                 │
             └────────┬────────┘
                      ▼
              Hardware Timing
              Timer / DMA
                      │
                      ▼
                  STEP / DIR
                      │
              ┌───────┼───────┐
              ▼       ▼       ▼
              X ...           B
```

The network stack, protocol parser, diagnostics, and other non-real-time firmware must be designed around the motion engine rather than allowing them to determine its timing behavior.

The final architecture must satisfy the fixed project requirements while providing substantial real-time performance and reliability margin.
