# CNC5AX-ETH Motion Engine

## 1. Purpose

This document defines the **non-negotiable requirements, constraints, interfaces, and design objectives** for the motion-control subsystem of the CNC5AX-ETH controller.

The purpose of this document is **not** to prescribe a specific implementation.

The final motion-engine architecture, algorithms, timer allocation, DMA strategy, buffering mechanism, interpolation method, and real-time scheduling strategy must be selected during firmware development based on:

- Mach3 SDK behavior
- Project requirements
- STM32F407 capabilities
- STM32 official documentation
- Real-time performance analysis
- Determinism
- Measured timing margin
- Reliability and safety

The implementation must satisfy all fixed requirements in this document with a substantial engineering margin.

# 4. STEP Outputs

## 4.1 Electrical Behavior

All STEP outputs are:

```text
Active High
```

A STEP event is generated by a transition from:

```text
LOW → HIGH
```

The external stepper/servo drivers are primarily sensitive to the **rising edge** of the STEP signal rather than the exact pulse width.

The STEP output therefore must guarantee a clean and deterministic rising edge.

---

## 4.2 Maximum STEP Rate

The maximum reliable target STEP frequency is:

```text
2 MHz
```

This means a maximum nominal STEP period of:

```text
500 ns
```

The 2 MHz figure is the project-level maximum target for reliable operation and must be treated as a hard performance requirement.

### Multi-Axis Requirement

The motion engine must be designed so that:

```text
At least 3 axes
```

can operate simultaneously at:

```text
2 MHz STEP rate per axis
```

while maintaining reliable and deterministic operation.

This is a **minimum guaranteed capability**.

The remaining two axes must remain fully functional and must not be architecturally disadvantaged simply because the minimum simultaneous 2 MHz requirement is specified for three axes.

A stronger implementation that supports all five axes simultaneously at or near 2 MHz is preferable, but it must not be assumed or claimed without verification.

---

# 5. STEP Pulse Width

The external stepper/servo drivers are primarily sensitive to the rising edge of the STEP signal.

Therefore, the exact STEP pulse width is not a primary system-level constraint.

The design should nevertheless maintain a pulse width comfortably above:

```text
100 ns
```

as a practical safety margin.

The implementation must ensure that the generated pulse is:

- Clean
- Monotonic
- Deterministic
- Free from unintended glitches
- Long enough to satisfy the external driver's requirements

# 7. DIR Timing Requirements

The minimum required timing margin for each direction change is:

```text
DIR setup time:  200 ns minimum
DIR hold time:   200 ns minimum
```

The implementation must guarantee at least these values between a DIR transition and the relevant STEP edge.

The actual firmware implementation should preferably provide additional margin rather than operating exactly at the minimum.

Conceptually:

```text
DIR change
    │
    ├────── ≥ 200 ns ──────►
    │
    │                        STEP rising edge
    ▼                              ↑
 DIR stable                first STEP event
```

The exact timing mechanism must be determined during implementation.

Software delays should not be used for hard real-time DIR timing when a deterministic hardware-based mechanism is available.

# 8. Hardware Timing Requirement

The STEP/DIR subsystem is a **hard real-time subsystem**.

The final architecture must ensure that Ethernet processing, application-level networking, diagnostics, logging, and other non-real-time operations cannot introduce unacceptable timing variation into STEP generation.

The repository architecture already establishes motion timing as a higher-priority concern than non-real-time processing.

The final implementation must preserve this principle.

# 9. STEP Pin Hardware Configuration

According to the project hardware definition (`Docs/PINOUT.md`):

```text
STEP_X = PC9
STEP_Y = PA8
STEP_Z = PA9
STEP_A = PA10
STEP_B = PA11
```

These pins have valid timer alternate-function mappings (PA8–PA11 = TIM1_CH1–CH4; PC9 = TIM3_CH4/TIM8_CH4), but per Section 10, they are deliberately configured as plain GPIO outputs and driven via DMA→BSRR rather than via their Alternate Function — because PA8–PA11 share a single TIM1 ARR (period), which would force axes Y, Z, A, and B onto one common STEP frequency.

The exact DMA stream/mask allocation must be taken from the authoritative project pinout and verified against the STM32F407 Datasheet and Reference Manual.

Do not infer timer/DMA assignments from the GPIO names alone.

## 10. STEP Generation Architecture

The STEP generation architecture is fixed as a **timer-triggered DMA to GPIO BSRR** design.

STEP outputs are configured as normal GPIO outputs. Timer PWM, Output Compare, Toggle mode, One-Pulse mode, and CPU-driven GPIO toggling are **not used** for STEP waveform generation.

The motion engine prepares time-ordered STEP events in DMA buffers. DMA transfers precomputed 32-bit values directly to the corresponding GPIO `BSRR` registers.

### Generation Path

```text
Motion Engine
      │
      ▼
STEP Event / BSRR Buffers
      │
      ▼
     DMA
      │
      ▼
GPIOx->BSRR
      │
      ▼
STEP Outputs
```

A base timer provides the deterministic DMA request timing:

```text
Base Timer Update Event
          │
          ▼
         DMA
          │
          ▼
GPIOx->BSRR
```

The timer therefore acts as the **DMA timing/request source**. It does not directly generate the STEP waveform and its output channels are not used as STEP outputs.

### BSRR-Based STEP Events

Each DMA transfer represents a predefined GPIO state transition. The transferred BSRR value may contain:

- GPIO set bits for STEP outputs that must become HIGH
- GPIO reset bits for STEP outputs that must become LOW
- Multiple axis transitions in the same transfer when required

This allows several axes sharing the same timing base to change state deterministically from a single scheduled event.

The STEP GPIO assignments are defined by `Docs/PINOUT.md`.

Current STEP output grouping is:

```text
GPIOA:
    PA8  = Y_STEP
    PA9  = Z_STEP
    PA10 = A_STEP
    PA11 = B_STEP

GPIOC:
    PC9  = X_STEP
```

Because the STEP signals are distributed across two GPIO ports, the implementation must account for both `GPIOA->BSRR` and `GPIOC->BSRR` transfers.

### Timing Requirements

The STEP generator must support:

- Maximum target STEP frequency: **2 MHz**
- Minimum guaranteed capability: **3 axes simultaneously at 2 MHz**
- STEP active state: HIGH
- Minimum practical STEP pulse width: greater than **100 ns**
- DIR setup time requirement: **200 ns minimum**
- DIR hold time requirement: **200 ns minimum**

At 2 MHz, the nominal STEP period is:

```text
T_STEP = 1 / 2 MHz = 500 ns
```

The implementation must preserve sufficient timing margin and must not depend on CPU execution latency for STEP edge generation.

### Determinism

Once a STEP event buffer has been committed for DMA execution, STEP timing must be independent of:

- Ethernet packet arrival timing
- LwIP processing
- UDP callbacks
- CPU scheduling jitter
- Background diagnostics
- Non-real-time application code

The CPU is responsible for preparing and managing motion data, while the timer-triggered DMA path is responsible for deterministic GPIO state updates.

## 11. Timer and DMA Resource Allocation

The STEP-generation architecture is fixed:

```text
Base Timer → DMA Request → GPIOx->BSRR
```

The exact STM32 peripheral allocation remains an implementation detail and must be selected according to the STM32F407VGT6 DMA request mapping, available DMA streams/channels, GPIO port usage, and conflicts with Ethernet and other peripherals.

### Fixed Architectural Requirements

The implementation must satisfy the following:

```text
STEP GPIO mode:
    GPIO Output Push-Pull

STEP waveform generation:
    DMA writes to GPIOx->BSRR

DMA timing source:
    Timer update event

STEP generation:
    Hardware-assisted

CPU-generated STEP edges:
    Not allowed

Timer PWM / Output Compare on STEP pins:
    Not used
```

### DMA Requirements

The DMA implementation must support deterministic writes to the GPIO BSRR registers.

Because the STEP outputs are distributed across two GPIO ports, the design must provide a suitable DMA transfer path for:

```text
GPIOA->BSRR
GPIOC->BSRR
```

The implementation may use separate DMA streams for the two GPIO ports, provided that both transfers remain synchronized to the intended motion timeline.

The exact DMA stream/channel selection is **TBD** and must be verified against the STM32F407 DMA mapping and all other active peripherals.

### Timer Requirements

The timer used for STEP DMA triggering must provide a deterministic update-event rate appropriate for the selected motion-event representation.

The timer is a **timing source for DMA requests only**.

The following must not be assumed:

- A timer channel must directly correspond to a STEP GPIO.
- A STEP GPIO must use a timer Alternate Function.
- PWM duty cycle is responsible for STEP pulse width.
- Output Compare directly drives STEP outputs.

Instead, the timer establishes the schedule from which DMA transfers update the GPIO BSRR registers.

### Resource Allocation Constraints

The final allocation must be checked for conflicts with:

- Ethernet MAC/LwIP DMA requirements
- Spindle PWM timer
- Other timer functions
- DMA streams and channels already required by the system
- GPIO availability
- Interrupt resources
- Memory/buffer placement and DMA accessibility

The final Timer/DMA selection is therefore an **implementation decision**, but the underlying architecture is not.

### Validation Requirements

The final implementation must be validated on real hardware for:

1. 2 MHz STEP operation
2. At least 3 axes simultaneously operating at 2 MHz
3. Correct STEP pulse width
4. Correct DIR setup and hold timing
5. Stable operation while Ethernet traffic is active
6. No missed or duplicated STEP events under maximum intended load

The 2 MHz requirement must not be considered verified from simulation, source code inspection, or theoretical timer/DMA capability alone.

# 34. Final Design Principle

The motion engine must be treated as the **highest-priority real-time subsystem** of the CNC controller.

The final implementation should follow this principle:

```text
                    MACH3
                      │
                      ▼
                Ethernet / UDP
                      │
                      ▼
               Motion Protocol
                      │
                      ▼
              Motion Processing
                      │
             ┌────────┴────────┐
             ▼                 ▼
        Axis Planning       Buffering
             │                 │
             └────────┬────────┘
                      ▼
           DMA →  GPIOx->BSRR   ← Base Timer Update Event
                      │
                      ▼
                  STEP / DIR
                      │
              ┌───────┼───────┐
              ▼       ▼       ▼
              X ...           B
```

The network stack, protocol parser, diagnostics, and other non-real-time firmware must be designed around the motion engine rather than allowing them to determine its timing behavior.

The final architecture must satisfy the fixed project requirements while providing substantial real-time performance and reliability margin.
