# Phase 2 Status — Ethernet / LwIP Bring-Up (M12)

**Date:** 2026-09-17
**Scope:** M12 `Communication/Ethernet` — PHY reset, link bring-up, static
IP, and the link state the rest of the firmware reads. Implemented against
the frozen decisions in `Docs/PRE-IMPLEMENTATION-DECISIONS.md` items 7, 8,
10 and 11, and ADR-011/ADR-012/ADR-013.

## 2. The static IP configuration had been silently reverted

The most important thing Phase 2 found was not new work — it was that work
already believed done had been undone.

`Docs/ETHERNET.md` §15 and §16 described the static IPv4 configuration as
`[FW-CONFIRMED]`, implemented across three files. It was, in commit
`438f59f`. Every one of those edits sat in a **CubeMX-generated region**,
and the regeneration in `b409ba5` ("replace tim8 with tim2") reverted all
three:

```text
lwipopts.h   LWIP_DHCP 0            ->  LWIP_DHCP 1
lwip.c       IP4_ADDR(...)          ->  ipaddr.addr = 0; dhcp_start(&gnetif);
lwip.h       IP_ADDR0..3 defines    ->  gone
CNC5AX-ETH.ioc  LWIP static params  ->  gone
```

There is no DHCP server on this link and there never will be
(`Docs/ETHERNET.md` §15), so the controller would have come up on
`0.0.0.0`, waited for a negotiation that could only time out, and been
unreachable — with the documentation still asserting it was configured.

**Fixed at four levels**, deliberately, because the single-level fix is
exactly what failed last time:

1. The `.ioc` carries `LWIP.LWIP_DHCP=0` plus the address fields again, so
   CubeMX itself regenerates correct code rather than being corrected
   afterwards.
2. The generated files are restored to the static-IP form.
3. `net_glue_apply_static_ip()` runs from `MX_LWIP_Init()`'s
   `USER CODE BEGIN 3` block and applies the address from
   `Net/Inc/net_config.h` regardless of what the generated code above it
   did — stopping DHCP first if a regeneration has re-enabled it. This is
   the level that survives.
4. `HV-24` fails if the running interface is not on the configured
   address, or if DHCP is active.

The same reasoning is why the MAC address is now re-applied from
`net_config.h` in `USER CODE BEGIN MACADDRESS`: the vendor placeholder
`00:80:E1:...` that ADR-011 removed is regenerated by CubeMX every time,
and `HV-23` reads the MAC filter register rather than trusting the C
literal.

**The general lesson, same as Phase 1's:** in this project a value is only
as durable as the block it is written in. `Net/Inc/net_config.h` is now the
single source of truth for the network configuration, and the generated
copies are treated as disposable.

## 3. What was built

```text
Firmware/
├── Net/                                PORTABLE - no STM32/HAL/CMSIS/lwIP
│   ├── Inc/net_config.h                IP, MAC, PHY timing, priorities,
│   │                                   with the invariants as static asserts
│   ├── Inc/net_link.h                  link observer interface
│   └── Src/net_link.c                  link state machine
├── Platform/STM32F407/
│   ├── Inc/net_hw_map.h                ALL network hardware allocation
│   ├── Inc/net_port_stm32f4.h
│   ├── Src/net_port_stm32f4.c          ADR-013 reset pulse, us delay,
│   │                                   NVIC/SRAM introspection
│   ├── Inc/net_glue.h
│   ├── Src/net_glue_stm32f4.c          the 3 calls the generated code makes
│   ├── Inc/net_selftest.h
│   └── Src/net_selftest_stm32f4.c      HV-20..HV-25
└── Tests/test_net_link.c               130 host checks
```

**Layering.** `Net/` has no hardware or lwIP dependency at all, which is
what lets the state machine be host-tested. The only thing above it is
`net_link_get()`, returning a plain struct — so when Phase 3 needs to know
whether the cable is in, or ADR-010's fault model needs a link-loss input,
neither has to include `lwip.h`. That is
`Docs/PHASE1-STATUS.md` §9 rule 4 applied in the other direction.

**Regeneration surface.** All logic lives in project-owned files. The
generated files carry three one-line calls, each inside a `USER CODE`
block:

| File | Block | Call |
|---|---|---|
| `LWIP/Target/ethernetif.c` | `USER CODE BEGIN MACADDRESS` | MAC from `net_config.h`, then `net_glue_phy_reset()` |
| `LWIP/App/lwip.c` | `USER CODE BEGIN 3` | `net_glue_apply_static_ip()` |
| `LWIP/App/lwip.c` | `USER CODE BEGIN 4_4` | `net_glue_poll_link()` |

If a regeneration drops one, HV-20/HV-23, HV-24 and HV-25 fail
respectively — which is the point of having them.

One detail worth recording: the link poll is called from the *trailing*
`USER CODE BEGIN 4_4` block, which runs at main-loop rate rather than every
100 ms, because CubeMX preserves only the markers it emits and there is
none inside its timer block. `net_glue_poll_link()` therefore rate-limits
itself to `NET_LINK_POLL_MS`. Putting a custom marker inside the generated
function would have been quietly deleted at the next regeneration.

## 3b. ADR-013 implemented

`net_port_phy_hw_reset()` drives `PB0` low for 150 µs, releases it, and
waits 1 ms before returning.

**The microsecond delay.** ADR-013 left the choice of primitive open;
`net_port_delay_us()` uses `DWT->CYCCNT` and enables the counter itself if
nothing else has. This runs during `MX_LWIP_Init()`, before
`stepgen_init()` enables the same counter for HV-04; enabling it twice is
harmless, and `CYCCNT` is deliberately not zeroed here because that counter
belongs to the motion engine.

**Placement.** The call sits *before* `HAL_ETH_Init()`, not merely before
the first MDIO access. `HAL_ETH_Init()` performs the MAC's DMA soft reset,
and starting that while the PHY is still held in reset invites a timeout.

**Datasheet facts established while implementing** (from this repository's
own `LAN8720A_DataSheet-DS00002165.pdf`, not from general knowledge):

| Symbol | Value | Consequence here |
|---|---|---|
| `trstia` (Table 5-9) | 100 µs min | ADR-013's 150 µs sits at 1.5× — the "~100 µs" in ADR-013 is exact |
| `tpurstd` (Table 5-9) | 25 ms min | Power-on only; not what this pulse addresses |
| `todad` (Table 5-9) | ≤ 800 ns | Output drive after release |
| §3.8.5 note | RMII runs at 2.5 MHz for the first 16 µs out of reset | The settle time must clear this |
| §3.8.5.1 | a clock must be present on `XTAL1/CLKIN` **during** reset | Satisfied: the module's own 50 MHz oscillator is independent of `nRST`, and also feeds the MCU's `PA1`, so asserting reset stops neither clock |
| §3.8.5.2 | software reset completes within 0.5 s (IEEE 802.3u 22.2.4.1.1) | Matches `LAN8742_SW_RESET_TO` = 500 ms in the ST driver — no mismatch |

**One implementation choice, flagged as such** per
`Docs/MOTION-ENGINE.md` Rule 2: `NET_PHY_RESET_SETTLE_US` = 1 ms is *not* a
datasheet minimum. The datasheet's only post-deassertion figures are
`todad` and the 16 µs RMII note; 1 ms is ~60× the latter and costs nothing
on a boot path. If HV-20 ever shows the PHY needs longer, it is one
constant.

## 6. Risks

### RISK-5 — Nothing here has seen a wire

Phase 2's honest position. Every claim above is about code that compiles,
links and places its buffers correctly. Whether this board negotiates a
link, answers a `ping`, or keeps STEP timing intact while doing so are
HV-20..HV-25 and HV-15, and all of them need the prototype PCB.

The single most valuable of them is **HV-15** — motion timing under
Ethernet load — because it is the empirical form of the project's central
rule. It could not be run before Phase 2 because there was no Ethernet
traffic to run it against. It can be run the day the board arrives.

### RISK-6 — The regeneration hazard is reduced, not eliminated

Phase 2 moves every network value into `USER CODE` blocks or project-owned
files, and adds tests that fail if a block is dropped. What it cannot
defend against is a regeneration that changes something with no `USER CODE`
block near it — the NVIC priorities in `HAL_ETH_MspInit()`, for instance,
which is why HV-22 reads them from the NVIC rather than trusting the
`.ioc`. After any CubeMX regeneration, run the self-tests before anything
else.

### RISK-7 — The link poll runs at main-loop rate

`net_glue_poll_link()` is called from a block that executes on every
iteration of the main loop and rate-limits itself with `HAL_GetTick()`.
That is a `uint32_t` millisecond counter comparison per iteration — cheap,
but not free, and it is in the same loop that will later carry the Phase 3
protocol. If the main loop ever becomes tight, this is a candidate to move
into the 100 ms block properly, which requires either a CubeMX-emitted
marker there or accepting that the call is re-added after each
regeneration.

## 7. What Phase 3 must not break

1. `Net/Inc/net_config.h` stays the single source of truth for addresses
   and the MAC. Do not reintroduce literals into the generated files.
2. The UDP port number, when decided, belongs in `net_config.h` beside the
   IP configuration — not in the protocol source.
3. Ethernet buffers stay in SRAM1 (ADR-012, HV-21). Anything Phase 3 adds
   to the RX/TX path is covered by the same rule; extend HV-21 rather than
   adding an exception.
4. `ETH_IRQn`/`ETH_WKUP_IRQn` stay numerically above `DMA2_Stream1_IRQn`
   (ADR-012, HV-22). Phase 3 adds protocol work in the Ethernet path; none
   of it may raise those priorities.
5. Read link state through `net_link_get()`, not by reaching into lwIP.
   ADR-010's `COMM_TIMEOUT` fault is a protocol-level timeout and is a
   different thing from a link-down event — `net_link_status_t` carries
   the latter, with `down_count` and `last_change_ms` available to tell a
   pulled cable apart from a quiet host.
6. Run the self-tests after every CubeMX regeneration, not only after code
   changes.
