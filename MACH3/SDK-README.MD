# Mach3 SDK — What's Actually in This Directory

This replaces an earlier version of this file that was a generic "how to use
any SDK" checklist, written before the zip below was extracted. Everything
here was verified by reading the actual extracted files, not assumed from
their names.

## 1. What's here

```text
MACH3/
├── Mach3 Software Development Kit(SDK).zip     — the original archive
├── Mach3 Software Development Kit(SDK)/SDK/    — extracted from the zip
│   ├── MachIncludes/                            — SDK's own bundled copy of the shared headers
│   ├── Blank Plugin/                            — AppWizard COM-DLL skeleton, I/O only
│   ├── BlankMovement/                           — same skeleton + ExternalMovement (motion-capable)
│   ├── Galil PlugIn/                            — real shipped plugin, Galil DMC-family motion controllers
│   ├── JoyStickPlugIn/                          — jog-input device plugin (no motion device)
│   ├── Probing/                                 — probing dialogs/behavior built on Mach3's own motion
│   ├── ShuttlePro/                               — HID jog-shuttle device plugin (no motion device)
│   ├── g100IO/                                  — Galil G-Rex terminal I/O plugin (jog, no ExternalMovement)
│   └── ncPod/                                   — real shipped plugin, USB motion "pod" device
└── Current Includes Files from Mach3 Software Develope Kit/
    └── MachIncludes/                            — a second copy of the shared headers
```

**Two copies of `MachIncludes` exist and are not identical.** Diffing them
turns up differences in exactly four files: `TrajectoryControl.h`,
`UDPSocket.h`, `Mach4View.h`, `resource.h`. The differences found so far are
minor (the `SDK/MachIncludes` copy's `TrajectoryControl.h` has a handful of
extra trailing struct members not present in the other copy; its
`UDPSocket.h` is missing one `#include` line) — nothing found so far changes
any fact this project relies on: `GMoves` (§3 below) is byte-for-byte
identical in both copies, and `UDPSocket.h`'s `CUDPSocket` class is
unaffected by its one-line difference. Still, **when quoting a header,
check both copies** — this project cites file+line against
`Current Includes Files from Mach3 Software Develope Kit/MachIncludes/`
unless stated otherwise, since that is the copy `Docs/MACH3-INTERFACE.md`
was written against.

## 2. The eight sample plugins — which ones actually matter here

All eight are Visual C++ 6/2005-era MFC/COM DLL projects generated by the
same AppWizard template (their `ReadMe.txt` files are the identical,
content-free AppWizard boilerplate — they describe the generated project
skeleton, not what the sample does, and are not worth reading). What each
one actually *is* has to be read from its source. Verified directly:

| Sample | Has `ExternalMovement.*`? | What it actually is | Relevant to CNC5AX-ETH? |
|---|---|---|---|
| `BlankMovement` | Yes | The bare motion-device plugin skeleton — every entry point (`SendHoldingMovement`, `GetInputs`, `SetOutputs`, `MyJogOn/Off`, `myDwell`, `HandleSequences`) with no logic filled in | **Yes — the entry-point reference**, §2.1 of `Docs/MACH3-INTERFACE.md` |
| `ncPod` | Yes | A real shipped plugin for a **USB** motion "pod" (`ncPODDriver.h`: "64 byte usb packets... through 2 different endpoints") | **Yes — the primary motion-encoding reference**, §4. Transport is USB, not Ethernet; only the *shape* of the motion data (fixed-time-slice per-axis velocity, fractional carry, ring-buffer drip feed) is what this project reuses |
| `Galil PlugIn` | Yes | A real shipped plugin for Galil DMC-family motion controllers, driven through Galil's own command library (`DMCMLIB`/`DMC32.lib`, `DMCWIN.CPP`), **not** through the `CUDPSocket` wrapper also present in this project (that wrapper is used by `G100Config.cpp`/`MessageTracker.cpp` for device discovery/configuration, not the real-time motion path) | **Yes — a second, contrasting motion pattern**, see §3 below and `Docs/MACH3-INTERFACE.md` §4a |
| `Blank Plugin` | No | The same AppWizard skeleton as `BlankMovement`, minus `ExternalMovement` — an I/O-only (no external motion) plugin base | No |
| `JoyStickPlugIn` | No | A jog-input device plugin (`JoySetup.cpp`) — reads a joystick and drives Mach3's own jog, not an external motion device | No |
| `ShuttlePro` | No | A HID jog-shuttle device plugin (`ShuttleWin.cpp`, `hid.lib`) — same category as `JoyStickPlugIn` | No |
| `Probing` | No | Probing dialogs and sequencing (`probing.cpp`, `ProbePoints.cpp`, `OkayToMove.cpp`) layered on Mach3's *own* motion, not an external motion device | No, unless/until this project designs its own probing UX |
| `g100IO` | No | A Galil G-Rex terminal I/O plugin (`GRexControl.cpp`) — has `myNotify`/`MyJogOn` but no `ExternalMovement`, i.e. I/O + jog only, no trajectory consumption | No |

**Only three of the eight consume `GMoves` trajectory data at all**
(`BlankMovement`, `ncPod`, `Galil PlugIn`), and only two of those are real,
shipped, non-skeleton implementations. The other five are useful only if
this project later needs an input-device or probing plugin of its own —
not for the motion/transport work this repository currently documents.

## 3. Two different ways a real plugin consumes `GMoves` — and which one this project follows

`ncPod` and `Galil PlugIn` solve "turn `MainPlanner->Movements[]` into
device commands" in genuinely different ways, both confirmed by reading
`ExternalMovement.cpp` in each:

- **`ncPod`:** waits for ≥32 queued moves, then flattens them into a
  **512-byte block of fixed-time-slice per-axis velocities** (`Send512Block()`,
  `SDVELOCITYMOVE` records), carrying each axis's fractional remainder
  between slices (`Pod->fractions[axis]`). The device (or here, the
  firmware) does its own interpolation from a velocity stream — Mach3's
  cubic/DDA math for that segment is not sent at all.
- **`Galil PlugIn`:** forwards `MainPlanner->Movements[Engine->TrajIndex]`
  **one move at a time**, sending each move's own `DDA1`/`DDA2`/`DDA3` cubic
  coefficients and `Time` — i.e. it relays Mach3's own segment math to the
  Galil controller's onboard interpolator, rather than re-deriving velocity
  itself.

CNC5AX-ETH follows the `ncPod` pattern, not the Galil one: ADR-007
(`Docs/FIRMWARE-ARCHITECTURE.md` §41) puts a DDA/Bresenham accumulator on
the STM32 itself, running from step-domain, time-sliced per-axis velocity —
there is no onboard consumer for raw cubic `DDA1/2/3` coefficients, so
relaying them the way `Galil PlugIn` does would just move the interpolation
problem onto firmware that isn't built to do Mach3's cubic math. This is
recorded as a deliberate choice, not an oversight, in
`Docs/MACH3-INTERFACE.md` §4a.

## 4. A concrete trap in the header names

`MachIncludes/InputSignals.h` and `MachIncludes/OutputSignals.h` are **not**
the input/output signal-table data structures — they are MFC
`CPropertyPage` dialog classes for Mach3's own config UI. The actual data
(`InputInfo`/`OutputInfo` structs, `Engine->InSigs[53]`/`Engine->OutSigs[30]`
arrays, sized by `Engine.h`'s own `#define nSigs 53` / `#define nSigsOut 30`)
lives in `MachIncludes/Engine.h`. This is exactly the kind of
name-doesn't-match-content mistake worth checking for before citing any
other header in this SDK by filename alone.

## 5. Where the project-specific summary lives

This file is an index of what exists, not a description of how this project
uses it. `Docs/MACH3-INTERFACE.md` is the maintained, project-specific
summary of the SDK facts this project actually depends on (plugin entry
points, `GMoves`, the `ncPod`/`Galil` consumption patterns above, the socket
API) and what CNC5AX-ETH concludes from each. Update that document, not
this one, when a new SDK fact changes a design decision.

## 6. Ground rules when reading further into the SDK

- Cite by file **and line**, from files actually opened in this directory —
  never from memory or from what a filename suggests (§4 above is why).
- If a fact matters to a design decision, it belongs in
  `Docs/MACH3-INTERFACE.md` with an `[SDK-CONFIRMED]` tag and its citation,
  not only in a code comment.
- Never invent an SDK function, struct field, or constant. If something
  can't be found in either `MachIncludes` copy or in one of the eight
  sample projects, say so explicitly (`[TBD]`) instead of guessing.
- Prefer the two real shipped plugins (`ncPod`, `Galil PlugIn`) over the
  skeletons (`Blank Plugin`, `BlankMovement`) as evidence for *how* an
  entry point is actually used — the skeletons show the shape of the API,
  not a working implementation.
